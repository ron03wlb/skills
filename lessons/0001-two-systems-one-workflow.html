兩套 skills，不是兩條流程

這堂課的 tangible win：你會得到一個不打架的心智模型，能把 Superpowers 與 Matt 放在不同層，而不是把同名 skills 全部串起來。

比較範圍是你目前本機的 13 個 Superpowers-derived Codex skills，以及 /Users/ron/Documents/Workspace/skills 這個 Matt fork 的 promoted skills。 不是對兩個品牌所有歷史版本的泛論。

先記住一句話

Superpowers 決定「怎樣做才安全可信」；Matt 決定「這件工作怎樣從想法走到交付」。

Superpowers：政策層

自動判斷 read-only、mechanical、standard、high-risk；守住授權、最小變更、 工作樹隔離、驗證與交付證據。

Matt：工作流層

由人選擇入口，透過 grilling、spec、tickets、TDD、review 與 issue tracker， 把模糊想法轉成可執行工作。

你的流程：責任層

以 Superpowers 包住 Matt；Wiki 保存現況業務基線，Matt spec 保存 change contract，code/tests 只保存實作證據。

為什麼不能直接相加？

兩套系統在五個地方重疊。如果沒有先指定 owner，agent 會產生重複訪談、重複 plan、 重複 TDD、重複 review，最後還可能把「已 commit」誤報成「已交付」。

重疊點 Superpowers Matt 你的 owner
需求釐清 brainstorming grill-with-docs 精確任務跳過；重大模糊才 grill，並維護 domain docs
規劃 writing-plans to-spec / to-tickets Matt spec 是唯一 change contract；plan 只補高風險操作
執行 executing-plans implement Matt implement 主導 ticket；Superpowers 提供授權與證據紀律
TDD / Debug 選擇性、授權清楚 seam、vertical slice、tight loop 更完整 各合併成一個 skill，不保留兩個並列入口
Review / 完成 風險 review、claim-to-evidence、branch finish Standards + Spec review，然後 commit 三軸 review，再由 finish-issue 分階段收尾

第一版整合流程

綠色守門規則在每一步都存在，但只有藍色工作流需要你主動選入口。

Risk / authority gate → Wiki + CONTEXT preflight → Grill if ambiguous → Spec if durable → Tickets if multi-session → Implement + TDD → 3-axis review → Evidence gate → finish-issue
最關鍵的刪減：小而精確的 standard task 不需要先 grill、寫 spec、拆 tickets。 它只需要明確 acceptance、最小實作、適當測試與證據。流程強度應由風險與跨 session 需求決定，不由「skill 存在」決定。

三個 retrieval prompts

先在腦中回答，再展開。能答對，才算開始建立 storage strength。

1. 為什麼 writing-plans 不能和 Matt spec 並列為需求權威？

因為同一變更若有兩份可獨立修改的需求文件，衝突時無法判斷哪份有效。Matt spec 應是 change contract；高風險 plan 只記執行順序、復原與驗證，並引用 spec。

2. 什麼任務應該跳過 grill-with-docs？

需求精確、repository evidence 足夠，而且不同解讀不會改變行為、範圍、架構或重要結果的任務。

3. Review 通過後，為什麼還不能說 Issue 完成？

Review 只證明 diff 的 Standards、Spec、Wiki 相容性。Merge preflight、baseline reconciliation、target verification、Issue closure 與 worktree cleanup 都是獨立 proof state。
