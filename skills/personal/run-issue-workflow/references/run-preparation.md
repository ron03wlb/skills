# Prepare before Run-ready

The planning owner inventories the actual operations before asking for any missing permission: installation paths, one task and worktree per selected Issue, follow-up execution and close messages, exact local target integration and cleanup, and tracker writes. Read current approvals first. Prepare the concrete operations and perform read-only host probes, then ask once for the remaining scope. Resolve approved decomposition keys to native Issue IDs without asking again for the same approved work. A new target, scope, ownership ambiguity or irreversible capability requires the concrete difference to be decided before that work proceeds.

`grilling` settles these decisions with the requirement. `to-spec` carries the approved inventory in its publication; `to-tickets` resolves it against the exact child mapping. The immediate producer owns the final preparation read-back before its Run handoff. Reuse `assessRunPreparation` in `scripts/run-preparation.mjs`; it computes missing approvals and SQL prerequisites and issues no authority of its own.

The existing `spec_publication` payload carries `preparation.requiredActions` entries with `action` and exact `scope` strings. Supported actions are `workflow-install`, `task-create`, `task-message`, `local-close`, and `tracker-write`. Its `preparation.trackerPublication.required` states the required publication semantics. The existing `producer_handoff.preparation.approvals` contains the same normalized entries plus each existing human `authority` reference. An entry is evidence of a previously granted operation; the producer must read that source, not generate an approval. These are fields in the existing producer handoff, not a generic authorization store or replacement Grant.

Probe the actual host's available task tools, saved Git project, tracker reads and exact installation state before presenting the proposal. A configured GitHub Issue publication uses immediate pre-read, write, and exact post-read; it is not atomic compare-and-set. If the requirement actually needs atomic CAS and the host does not supply it, resolve that capability gap during planning. Never label an unsupported `If-Match` write as CAS. An uncertain write is read back before any retry, and conflicting or ambiguous ownership remains preserved.

## One declared Manual prerequisite

No SQL requirement means `sql: []`, reported as `N/A`, with no SQL question, task, artifact or database dependency. Never discover a requirement by scanning arbitrary `.sql` files.

For a declared human-applied artifact, the publication's `preparation.sql` contains its exact `issueId`, normalized `artifact`, and opaque `environmentIdentity`. Settle the environment, authorized effect and permissions, operator, recovery and `APPLIED`/`NO_OP` validation before preparation. Environment identity is a human-confirmed declaration, not a database probe or credentials. Changing it requires fresh attestation.

After publication gives the exact Issue identity, the planning owner hands that same Issue to `pre-execute-issue` before exposing its ready state. Use its existing artifact candidate, validation, independent review and human application flow. A planning handoff may establish the one prerequisite task/worktree when already covered by the approved inventory. Its native initial prompt includes `Workflow prerequisite lane: <JSON>` with `issueId`, `specId`, `target`, and `approvedScopeHash` in that order. Preserve this task and worktree for later execution; it is not another product lane.

Carry the existing candidate packet in `producer_handoff.preparation.preparedSql`: exact Issue, environment, artifact, candidate, blob, `owner`, `recoveryPrepared: true`, `validation: passed`, `standards: clean`, `spec: clean`, `outcome: APPLIED|NO_OP`, immutable `attestationIdentity`, `taskRef`, `worktree`, and `topic`. Read every field from its owner. The new environment-bound v2 note adds `environment_identity` to the existing candidate/blob/path/outcome attestation; it contains no credentials, connection details or SQL contents. Older environment-less v2 remains limited to its exact older declaration and cannot satisfy this new environment-bound handoff.

The installed reader verifies the exact trusted attestation, Git object types, path/blob, branch/worktree and ancestry. It adopts the prepared native task after prompt and Git common-directory read-back, then sends the first execution request under the subsequently read-back Run Grant. An uncertain message is reconciled before retry. No second task/worktree or repeated same-scope approval is needed. Completion and close re-read the attestation and candidate ancestry; new environment or artifact content invalidates it only for the affected Issue and dependants of an existing Run.

Known missing preparation prevents a fresh Run from becoming ready. The planning owner completes it and returns its normal handoff. Late, previously unknown prerequisites use the existing same-lane handoff and expose only the newly required decision. A Run Grant never authorizes SQL application, recovery, deployment or external cleanup.
