For Windows x64 `EBUSY`, `EPERM` or `EACCES`, this close owner has the bounded repository adapter below. It proves the exact helper processes independently of native release capabilities. Policy rejection, unknown ownership and unsupported hosts remain blockers. Never terminate arbitrary processes, patch the host or copy historical PIDs.

It rechecks common directory, target cleanliness/ancestry, topic, unregistered ordinary empty path and exact idle task, then rechecks ownership after the native read. Unknown/running/foreign tasks, linked/nonempty paths and failed reads remain blockers. Idle metadata proves neither helper ownership nor respawn protection. The helper performs no filesystem, tracker or process mutation, including when a helper respawns during the read.

Release the target writer then repository close lease in the close owner's existing `finally` boundary. Read both leases back; retain any release failure alongside the original observation and preserve unresolved ownership. Do not roll back integration, invalidate completion, create an implementation-blocked note or replay verification.

It keeps completion valid and isolates only the affected Issue/dependents. An unchanged host blocker spends no continuation attempts; unrelated target movement does not resolve it. The same close owner resumes after supported host recovery yields new owning-source evidence, or physical absence permits the remaining tracker action. ## Exact Windows helper recovery

An authorized closeout includes one bounded recovery of its completed task's verified helper processes. An older retained package keeps its original rules; adopt this behavior only through the existing authorized package-maintenance path or an explicit human host-repair request. Historical grants and package files stay unchanged.

Once the original Issue task is idle with a completed latest turn and both previous leases have released, invoke `recoverPendingHostCleanup` from [the close-owner helper](../scripts/pending-host-cleanup.mjs) in a process outside the Issue directory. A coordinator may invoke this owner entry from its target checkout; the helper alone acquires the original operation's repository lease and target writer. Keep the Issue task idle during recovery: sending it another cleanup message can recreate the very helpers holding the directory. This is not a replacement task or a coordinator-preacquired lease.

Pass the exact close `leaseInput`, unchanged `completion`, original `taskRef`, a fresh native `readTask(taskRef)`, the original OS `failure`, and `verifyIntegration(leases)`. The latter calls `verifyIntegratedCandidate` with the original execution operation and every approved integration check, using fresh inputs and existing passing evidence. It must return the current identity-bound PASS; cached prose, ancestry or a synthetic `PASS` object is not verification. Changed inputs retain the existing integration owner; recovery does not remove or skip obligations.

The helper first proves ordinary empty unregistered path/topic ownership, candidate ancestry, clean target, settled task and integration PASS, then tries ordinary nonrecursive removal in case the lock already disappeared. A remaining OS lock enters its private PowerShell child, which reads native x64 process parameters and duplicates only each matching current-directory handle for read-only path verification. The layout self-probe, exact executable/entrypoint, parent chain to the existing Codex host, creation time, command digest and absence of foreign child processes bind one frozen helper set. Supported kinds are the installed Codex Node REPL, computer-use launcher, template picker and local codebase-memory helper. Names, an idle flag or a matching path in arbitrary command arguments alone are insufficient.

Task, Git, lease and integration facts are re-read after discovery before release. A private `exact-helper-recovery:v1` reservation under the Git common directory records this completion/task before effects; an existing reservation prevents another automatic process batch, including after a lost response. Ordinary directory removal remains retryable when its lock disappears. Termination uses retained Windows process handles, with fresh task, directory, process and child-inventory checks before each stop, so PID reuse cannot select another process. Each observed outcome is flushed before authorizing the next stop; an audit failure preserves known effects and stops the batch. Release is bounded to that set. New holders/children, unreadable relevant processes or changed identity stop; observed respawn is recorded without chasing it. The adapter detects respawn; it does not claim to prevent the host from starting processes.

After release, re-read task/Git/integration ownership and remove only the exact empty directory nonrecursively. Actual physical absence proves cleanup, including when an unobserved foreign handle kept removal blocked. Preserve original errors, the reservation and any partial result. `HOST_CLEANUP_RECOVERED` is cleanup evidence only: reconcile the same Run and let its original close task perform any remaining tracker action from the target checkout after the usual current integration checks. `host_helper_recovery_failed` retains `HOST_CLEANUP_BLOCKED`; fresh operator diagnosis owns any further attempt. Neither outcome changes candidate, completion, review, repair-wave counts or tracker state inside the helper.

A frozen launcher can exit naturally after its child is released. The inspector observes that exit through the original retained kernel handle and records `EXITED` with `TerminationRequested: false`; it does not reread the exited process's parameter buffer or select a replacement PID. The remaining live helper set still requires exact directory, ancestry and child-inventory validation. An unreadable live process remains a blocker. Native parameter-read errors report the process ID, read phase, field category, OS error and byte counts without addresses or command text.

A repaired adapter does not erase an earlier reservation or authorize an automatic second batch. A separately authorized operator continuation preserves the old reservation, partial outcomes and original remaining identities, records its new authority and audit separately, and uses the same close-owner task/lease/integration gates. Any new holder, changed creation time, ambiguous old outcome or live child of an exited ancestor must return to diagnosis before another process effect.
