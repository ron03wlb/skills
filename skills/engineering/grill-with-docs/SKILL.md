# Grill with Docs

Bind one proposed Tracker Spec, target, and starting baseline before the interview. Read-only exploration and tracker-only settled scope need no worktree, lane, or task identity. Before creating a lane or accepting the first glossary or ADR write, resolve a stable opaque `taskId` from the active host context; never ask a human to provide, guess, or confirm it. Create or reuse one **Spec workflow lane** only after that host resolution: one host-resolved task identity owns one proposed Tracker Spec, one target, and one isolated planning worktree. If the host cannot provide a stable identity, stop before the lane or write with `host identity unavailable`, preserving the settled design, frontier, and retry information; a human-supplied value cannot bypass that blocker. A mismatched host-resolved task identity, Spec, target, worktree, or baseline is a Recoverable blocker; name the lane registry, observed evidence, smallest human action, and preserved stages, then retry the same `/grill-with-docs` command.

Two lanes may grill against the same target without a shared planning checkout, global workflow lock, or cross-lane state mutation. Keep accepted document edits inside the lane; the target checkout and every other lane remain untouched. This skill creates only a local proposed-Spec/lane identity: it never reserves or publishes a Tracker Spec or Issue. `/to-spec` alone owns Tracker reservation and publication.

Load "grilling" and "domain-modeling" as separate named skills: use the generic Skill tool when available; otherwise use the host-supported mechanism to read and follow each required `SKILL.md`. Keep the selected source and invocation restrictions, passing the same settled scope and, when writing accepted decisions, the same lane identity to each. This invocation delegates evidence-backed reversible design choices and their qualifying document writes within the agreed goal; an explicit read-only or review request narrows that scope.

Pass a **boundary-first decision aperture** to both skills. Reserve new or changed overall direction, architecture, and persistence boundaries for the human: table creation or any table DDL; split, merge, ownership, aggregate, system-of-record or destructive lifecycle; and major module, system, external-contract, trust or authorization direction. Any migration cost also reaches the human frontier under `grilling`'s migration rule. Evidence and conventions support a recommendation; only an applicable accepted decision settles a reserved choice without asking. Scope or operation permissions and costly or irreversible commitments retain their shared gates. Within settled boundaries, resolve ordinary business and implementation details from explicit decisions and project contracts, then source conventions, then suitable established practice. Multiple plausible answers alone do not create a human question. Carry concise defaults, sources, reasons, practical reversal and verification assumptions in the handoff.

Apply `grilling`'s SQL boundary and decision presentation: table DDL, data corrections, destructive or costly SQL and migration costs require the missing approval; routine reversible queries and bindings are delegated. Bring each reserved choice as one concrete proposal with alternatives, trade-offs, reasons and a recommendation. Group independent human questions; retain any pacing limit the user explicitly requests.

When Pi exposes `ask_user_question`, use it only as an optional presentation for ready, independent human-frontier leaves; its availability never widens the aperture. Put 1–4 leaves in a dialog and split later leaves into the existing next round. Each leaf is one single-select question with a short header, a question-ending prompt, and 2–4 distinct options: up to three substantive proposals that preserve the proposal, alternatives, effects, trade-offs, migration cost, recommendation, and evidence, plus a fixed `Explain` option. `Explain` does not settle a decision: provide that leaf's context, evidence, trade-offs, and recommendation, then ask that leaf again. Free text or a substantive option settles a leaf only when it states a clear human decision; ambiguous text or a newly reserved boundary stays unresolved for clarification. A user cancellation settles none of that dialog's leaves and preserves the lane and frontier for this same-command retry; no UI, load, or validation failure preserves the leaves and falls back to the existing text questions. Neither dialog answers nor explanation grant document writes, SQL, implementation, publication, or handoff authority beyond an otherwise accepted decision.

`domain-modeling` records each accepted glossary or ADR change in the isolated planning worktree as it settles. Accepted includes inherited decisions, explicit human decisions, and choices made under the scoped delegation; record their actual basis and source without labeling delegated choices human-confirmed. Unaccepted proposals stay in the conversation. Use project document conventions; record durable rationale in ADRs and carry precise behavior, numeric defaults, exclusions, and verification needs in the settled scope for `to-spec`.

At the end, create an exact handoff packet containing the host-resolved opaque `taskId` for a document-writing lane, the proposed Spec, target, current baseline, and an explicit empty change list for tracker-only work or the owned worktree and every accepted glossary or ADR path or hunk with its content identity. The `taskId` is lane provenance, not a Tracker Issue ID, and consumers compare it only for equality. Tell the human to run `/to-spec` with that handoff packet. Keep the lane registered through publication. The `to-spec` owner disposes of only this exact clean planning worktree through its own lane-disposal action, after the successful `to-spec` handoff read-back; a partial publication, uncommitted accepted decision, identity mismatch, or failed read-back preserves it for the same-command retry.

Include each decision's basis and source, remaining verification assumptions, exact non-ADR requirements, and any SQL approval and prerequisite ordering in that existing packet. Finish without a second confirmation of already settled choices. The packet grants no implementation, SQL execution, or automatic publication authority.
