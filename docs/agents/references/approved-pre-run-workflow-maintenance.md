# Approved pre-Run workflow maintenance

Read this reference only before any Run Grant exists, when a human-approved Spec identifies one exact maintenance Issue. An explicit Start retains only already-approved operations for its exact Spec revision; separate maintenance execution needs no second human command. A product worker never repairs its governing runtime.

The active Codex task reads the original human selection and accepted revision from the current conversation/task, exact maintenance Issue and operation scopes, and current Pause/Stop/revocation state. It supplies one transient human handoff, not a journal or Grant. A label, title, generated packet, or remembered success cannot prove authority. Missing human/control evidence stops.

Call `createGitHubWorkflowSources(...).readBootstrapHandoff({specId, human, control})` from the reviewed trusted source. This read-only adapter rereads current publication, decomposition, completed producer checkpoint, approvals, blockers, existing journals, and Git/leaf completion evidence. Its `run-preparation.mjs` owner returns only the next legal owner action; it never dispatches, creates a Grant, or installs code. An untrusted or modified package cannot supply recovery.

Human input binds `repositoryId`, `specId`, `issueId`, `target`, `approvedScopeHash`, `decompositionIdentity`, `startAuthority`, and exact `operations`. `startAuthority` is the current producer approval whose original human source was read; operations are approved action/scope pairs. Control binds that authority, `connected: true`, and `state: ACTIVE` only while live human/task state permits continuation. Re-read sources before every action; time or a prior process ending never makes control active.

- **EXECUTE:** invoke `execute-issue` with this exact continuing human maintenance handoff and preserve deterministic operation identity. The execution owner reads existing progress/task/worktree and creates only a proven missing lane; uncertain task creation resolves through exact native input and Git ownership. The maintenance leaf retains normal candidate, verification, review, and completion.
- **CLOSE:** reuse valid completion and invoke `close-issue` with the same handoff. The close leaf alone owns repository/target leases, integration, exact clean-worktree cleanup, and closure. Preparation/execute do not perform these actions. Re-read partial progress and reuse the original candidate; completion is not permission to replay execution.
- **CONTINUE:** maintenance completion, reachability, worktree absence, and tracker closure agree. Recheck installed package, launch the same selected entry/active host driver, then obtain normal READY reduction and read-back Grant before product dispatch. Existing leaf completion is a succeeded node without duplicate lane. No second Start is required.
- **BLOCKED:** preserve evidence and report the missing authority, ownership, control, or stage. Existing Runs use original Grant/reconciliation. New scope, unknown ownership, Pause, Stop, revocation, or disconnected host never gains authority here.

Installation remains its own reviewed operation and starts no Run. Pending intent, catalog, package, and known-link backups own install retry; execution/close records own maintenance retry; the journal owns later Grant. Observe the owning source after uncertainty. This reference adds no generic repair runner or second receipt framework.
