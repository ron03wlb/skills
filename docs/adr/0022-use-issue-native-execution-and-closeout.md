# Use Issue-native execution and closeout

Retain `execute-issue` and `close-issue` as an explicit alternative within Matt's existing Issue flow. Ordinary `to-spec` and `to-tickets` create the tracker work and `/implement` remains the default implementation step. When the user explicitly selects the worktree alternative, each dependency-ready Issue is implemented in its own worktree, reviewed for Standards and Spec, and repaired for at most ten waves by `execute-issue`; a separately invoked `close-issue` refreshes and fast-forwards the original local branch, removes the clean Issue worktree, and closes the Issue.

Remove `ask-ron`, `to-spec-ron`, `to-tickets-ron`, and their hashed contract and lifecycle-authorization envelopes. Direct invocation covers one local execution or closeout, a human serializes integrations per target branch, and a plain tracker completion note hands the reviewed candidate between the two skills. This gives up machine-verified authorization lineage in exchange for the smaller Issue-native flow while retaining clean-worktree checks, exact Git identities, separate Standards/Spec review, and exclusions for push, remote merge, deploy, and unrelated deletion. `/wiki` and `/remove-ron` remain independent controls.

Clean-worktree checks apply to the reviewed Issue candidate, not to the original target worktree as a whole. `close-issue` may fast-forward a target that contains unrelated staged, unstaged, or untracked work only after a read-back `PREPARED` completion-note receipt binds the target-before, candidate, canonical dirty digest, and non-sensitive counts. Candidate and dirty rename sets include both endpoints, and collision checks use NUL-safe repository/filesystem path semantics. Target or digest drift stops the invocation. A matching post-fast-forward digest promotes the receipt to read-back `VERIFIED`, which gates worktree cleanup and Issue closure; matching `PREPARED` retries may recover only from the recorded target-before or candidate state, and every other receipt/target state stops. No path or file content enters the receipt, and no failure triggers automatic stash, commit, cleanup, refresh, rollback, or repair. Issue work may proceed in parallel, while integration is serialized only per target branch.
