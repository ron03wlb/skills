# Separate execution, closeout, and push verification

Each Issue records the branch from which its dedicated worktree was created. Any number of `execute-issue` runs may continue concurrently, and movement of that target branch alone does not invalidate a successful execution candidate; one `close-issue` writer per target requires the target worktree to be clean, directly merges the unchanged reviewed candidate into the latest target without an isolated integration candidate, then removes the clean Issue worktree and closes the Issue. The merge fast-forwards when possible and creates an ordinary merge commit only for diverged histories; it never rebases, squashes, refreshes the candidate, or creates a history-only marker. Git ancestry, worktree registration, and tracker state make those three outcomes idempotent without custom closeout receipts: retry skips only a satisfied ordered prefix, while missing identity, a dirty Issue worktree, or contradictory and out-of-order state stops without reopening, reconstructing, deleting, or otherwise repairing state. A dirty target stops the next ordered closeout action and resumes through `close-issue` after the human makes it clean; whether observed before or after merge, it never invalidates the candidate or routes back to `execute-issue`. A merge conflict is aborted and keeps the Issue worktree and Issue open; `close-issue` never repairs or reruns execution, but the human or same authorized coordinator may start a new `execute-issue` attempt in that same branch and worktree from the latest target, resolve within the original Acceptance Criteria, and publish a newly reviewed candidate. That attempt's latest-target baseline and candidate become current through the new read-back completion note, while ordinary target movement starts no attempt and supersedes nothing. The coordinator journals a persistent maximum of ten conflict repair waves, retains the original task/worktree, and requires fresh verification and both review axes for each replacement candidate. A conflict that changes behavior, Acceptance Criteria, target, exclusions, or ownership returns to planning instead. A new ordinary merge combination receives the integration checks required by its approved plan before cleanup; unchanged execution results can be reused with exact input-validity evidence. This remains separate from aggregate push verification. `/verify-target-before-push` retains one public name but has two evidence modes: by default it freezes the non-empty local unpushed range from the target's unique upstream tracking tip to local `HEAD`, while already-pushed work requires an explicit merge request, pull request, or exact base/head range and never guesses. It classifies completion-note candidates against exact `B` and `V`: reachable post-baseline candidates are members and require closed Issues, open unreachable candidates remain concurrent work outside the selected range, and closed unreachable candidates block as contradictory delivery evidence. Read-back completion notes are the sole Issue-to-commit mapping authority and bind each exact baseline-to-candidate contribution by SHA and ancestry; commit-message text is ignored. Every material range commit must have at least one member, referenced Planning Seal or prerequisite, or necessary merge-topology explanation, while overlapping contribution ranges are valid and require no unique owner. Focused verification normally reruns every deduplicated member command at exact `V`. An earlier path-specific command may instead use **Successor verification evidence** only when a later member candidate descends from the earlier candidate, the later Acceptance Criteria explicitly retire every repository path named by that command, its completion evidence proves those paths absent and current replacement behavior passing, and the paths remain absent at `V`; partial ownership, inferred deletion or rename, a non-path-specific command, or missing proof stops the gate. The result records the superseded command and exact successor proof, preserving the historical completion note rather than rewriting it or restoring retired files. Both modes perform aggregate review and verification once; only local-ahead mode may issue `push_ready`, while explicit already-pushed mode returns a range verification result. This responsibility split supersedes the isolated integration-candidate, closeout-receipt, and target-drift feedback behavior described by ADR-0022 and ADR-0023, preventing execute/close retry loops without introducing a queue, daemon, or lock service.
