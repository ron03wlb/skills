# Reconcile closed Issue evidence without retroactive completion

An already-closed Issue whose immutable completion note records non-passing final verification cannot be made historically implementation-complete. A separately human-authorized, append-only **Closed Issue evidence reconciliation** may repair only that Issue contribution's eligibility for aggregate target verification; it never edits the original note, invokes **Direct target contribution recovery**, waives a failure, or claims that the historical candidate passed. We chose this boundary over reopening an Issue merely to fabricate a no-delta candidate, rewriting historical evidence, or treating a later target pass as proof of earlier candidate completion.

The reconciliation separates non-authorizing **Reconciliation diagnostics** at the exact execution baseline and candidate from authorization-bearing **Reconciliation verification** at the exact aggregate target. Diagnostics may reproduce the same pre-existing failure fingerprint, but any different fingerprint or additional candidate failure stops; every reconciliation verification command must pass. This exception repairs no ordinary Issue lane: a candidate with non-passing final verification still cannot become `implementation_complete` or enter normal `close-issue` merge.

Eligibility also requires one exact closed **Reconciliation remedy Issue** whose published scope and delivered diff explicitly own the original failure, whose completion evidence is valid and passing, and whose candidate is reachable from the same exact target as the affected candidate. An aggregate target that merely passes, a human cause attestation, or a direct target contribution cannot substitute for that ownership chain; when no qualifying remedy Issue exists, correction returns to normal Issue delivery.

Version 1 accepts exactly one non-passing command in the original completion note, one unchanged failure fingerprint at baseline and candidate, no additional candidate failure, and one remedy Issue that owns the whole correction. Multiple failed commands, fingerprints, additional failures, partial ownership, or multiple remedies stop and return to normal Issue delivery rather than widening reconciliation into a generic verification waiver.

The diagnostic fingerprint is structured and human-readable: the exact command, exit code, failure count, ordered failure identities, source locators, and assertion or error identities must match at baseline and candidate. Timing, duration, temporary paths, stack noise, and full raw logs are excluded, and no opaque output hash substitutes for readable evidence. A runner result without one deterministic comparable failure identity is ineligible and stops.

`verify-target-before-push` owns discovery and preparation of this recovery. After read-only eligibility checks, it presents the complete append-only authority-record draft and requires one exact human confirmation; a separate model-invoked helper writes and reads back only that confirmed record, then the verifier automatically restarts from Entry. Aggregate verification, including the repository full suite, runs once on the freshly frozen exact target, so the helper neither verifies nor claims push readiness. We chose this over a second public reconciliation command, reuse of `attest-target-contribution`, or mutation followed by in-place continuation of the stopped gate.

That model-invoked helper is `record-closed-issue-reconciliation`. It accepts only the verifier's exact confirmed packet, revalidates tracker location, target, completion note, diagnostics, remedy identities, refs, and drift, then reuses an exact record or appends and reads back one new record. It never discovers the case, decides eligibility, requests confirmation, runs diagnostics, review or tests, changes Issue state, edits history, starts verification, or claims readiness; the active verifier invokes it automatically after confirmation, without another human slash command.

The helper's only legal invocation point is after member derivation on a frozen range has proved the one-to-one historical case and the human has confirmed the exact draft, immediately before fresh verification Entry. An open or unintegrated Issue, ordinary execution or closeout failure, selected-range coverage failure, aggregate review or verification failure, multiple affected identities, evidence drift, or absent confirmation never invokes it; those states retain their existing owner and failure path.

The append-only authority record binds the affected Issue and immutable completion note, target branch, execution baseline, affected candidate and single failure, remedy Issue and candidate, and exact human authority, but not the aggregate verification baseline or target. Each fresh verifier freezes its own range and requires both candidates reachable before running current aggregate verification; normal descendant target movement therefore needs no duplicate record, while rewritten history that drops either candidate makes the record inapplicable. Exact range refs and passing results belong only to the resulting Push-ready receipt or Range verification result.

The helper appends this record only to the affected closed Issue's ordered tracker history and reads it back there without reopening the Issue. The record references the remedy Issue; it is never written instead to that remedy or to their parent Spec, because either location would require reverse inference or mix corrections for multiple children.

The one `closed_issue_evidence_reconciliation:v1` comment contains only the affected Issue, target branch, original completion-note identity, execution baseline and candidate, exact failed command, structured baseline and candidate diagnostics, remedy Issue scope, completion-note identity and candidate, `authorized_by: human`, and the target-membership-only statement that the original completion remains invalid. Aggregate refs, push readiness, current verification results, full logs, output hashes, and worktree paths are absent. Repository docs and tests may show placeholders or examples, but the tracker receives only the fully populated live record after diagnostics and exact confirmation.

An exact matching read-back record is reused without another write. A missing record may be appended once after confirmation; malformed, duplicate, edited, conflicting, mismatched, unavailable, or partially written evidence stops without accepting a subset or manufacturing replacement authority. Neither the helper nor verifier edits, deletes, repairs, or supersedes tracker history.

The same reconciliation recovery is available in both verifier evidence modes because both use the same eligibility, confirmation, fresh-entry, aggregate-review, verification, cleanliness, and ref-stability gates. Local-ahead mode alone may issue a Push-ready receipt; explicit already-pushed mode returns only a Range verification result and never retroactively grants push readiness. Neither mode guesses a range or weakens its existing result boundary.

The affected Issue must already be closed, its candidate must be a selected-range member reachable from the exact target but not baseline, and its recorded Issue worktree must be absent from the Git worktree registry. Its immutable note must be the sole available completion mapping and invalid only for the one historical command; a later valid completion, another candidate-invalidating fact, an open Issue, a registered worktree, or an unreachable candidate returns to the normal owner or stops as contradictory evidence. The remedy Issue must likewise be closed with its valid candidate reachable from the exact target. Reconciliation exists only after the ordinary execution and closeout lane has ended.

The affected note's Standards and Spec review evidence must already be complete, clean, and bound to the exact unchanged candidate; reconciliation preserves that historical review rather than rerunning Issue execution. Any missing, ambiguous, unclean, or differently bound review is another invalidating fact and makes the case ineligible. Fresh target verification still performs aggregate Standards review and every member Spec review on exact `B...V`, so preserved candidate review never substitutes for current composition review.

Fresh verification collects every exact command from the affected note, not only the historically failed command, deduplicates exact matches with other members, and requires every executed command to pass at the freshly frozen target. A command identical to the repository-required full suite is executed only once in the full-suite stage. Free-text observations remain non-authorizing history and never enter the command set or replace a required command; a required verification represented only by prose makes the case ineligible.
