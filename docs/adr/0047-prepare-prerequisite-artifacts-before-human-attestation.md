# Prepare prerequisite artifacts before human attestation

`pre-execute-issue` remains the only public prerequisite entry, reached only for an exact **Manual prerequisite** artifact declared by the Issue or Spec or discovered during execution and resolved to an exact repository-relative path; no declaration skips the workflow, and arbitrary `.sql` files never trigger it. A direct invocation may derive the recorded Issue target, create or reuse the unique Issue topic branch and worktree, and later commit only the exact declared prerequisite artifact; dirty, mismatched, or ambiguously owned state stops without cleanup. When the exact artifact is not ready, `pre-execute-issue` automatically invokes the separate model-invoked `prepare-prerequisite-artifact` helper. That helper calls repository adapter operations; the adapter is repository code, not a skill or human command. Repository onboarding or an explicitly authorized setup Issue installs and validates one repository-owned adapter with read-only `discover`, artifact-writing `prepare`, and read-only `validate` operations; runtime prerequisite workflows only consume it, and a missing, broken, or incomplete adapter stops without creating or modifying infrastructure inside the product Issue. The adapter reports database product, version, target environment, authoritative inputs, diagnostics, and pass conditions rather than forcing a universal profile schema, and it owns the matching database-native executable assertions for preconditions, backup integrity, and postconditions plus the locking and transaction strategy needed to prevent state drift. The helper uses that evidence instead of asking the human for per-run paths or guessing a dialect; only missing or contradictory evidence that would change the artifact returns one focused decision. It creates or repairs the repository artifact, reruns `validate`, and obtains independent Standards and Spec review after each material edit. Deterministic failures and **Confirmed code review findings** share one budget of at most ten material repair waves; advisories remain visible but do not block, tool failures and retries without an artifact edit do not consume a wave, and wave ten still failing either required axis stops without presenting the artifact as ready. The helper never executes SQL or mutates an external environment: only an exact artifact with every deterministic check passing and no confirmed finding may become a clean committed **Prerequisite candidate** in the Issue worktree and be presented for human execution. Normal operation presents one primary three-section **Operator SQL**; its recovery statements remain commented and inert, and irreversibility is stated rather than hidden behind a fabricated rollback. The candidate commit, Git blob, and repository-relative path bind the generated content without a duplicate SHA-256 record. Successful SQL completion emits exactly one terminal outcome, `APPLIED` or `NO_OP`; the human reports only that value, without database version, path, hash, or complete log, and the content-bound `manual_prerequisite_complete:v2` records it with the exact candidate, Git blob, and path. A generic success statement receives one focused outcome clarification; a failure needs only its error text. Legacy path-only v1 attestations remain readable but cannot authorize a newly generated artifact. Either successful outcome authorizes continuation without independently proving external state. A reported execution failure, SQL error, or missing or unknown outcome writes no attestation, resumes no Issue execution, and triggers neither automatic retry nor rollback: read-only diagnosis must first establish the possible external state, and only separate correction authority may produce another fully validated and reviewed prerequisite candidate. When an already-authorized active `execute-issue` invoked this prerequisite flow, exact attestation read-back returns control to that same execution lane only after fresh Issue, target, artifact, candidate, blob, branch, and worktree checks. A directly invoked `pre-execute-issue` stops after attestation and never grants implementation authority; later `execute-issue` reuses the same worktree and requires the prerequisite candidate in its final ancestry. Neither path integrates the target, closes the Issue, pushes, or expands preparation beyond the declared artifact. This supersedes ADR-0039's no-preparation boundary while preserving its human-only attestation authority.

The primary **Operator SQL** has exactly three ordered sections: a read-only preflight that aborts when execution conditions fail; a backup of exact affected data with validated recovery statements present but commented and inert; and only then the authorized mutation or insertion plus applicable postconditions. Repeated invocation uses a three-state preflight. An absent backup plus repository-defined pre-mutation state permits the first backup and mutation. An integrity-valid existing backup plus complete postconditions returns successful no-op without deleting the backup or performing another mutation. Every partial, contradictory, or unproved combination aborts, so an already-started or already-applied operation is never treated as a fresh execution. Every precondition, backup-integrity check, and postcondition is a database-native fail-closed assertion emitted for the discovered database product and version; mismatch terminates the SQL with an error, and diagnostic `SELECT` output is supplemental rather than an operator-judgment gate. After the persistent backup is created and validated, the adapter revalidates and locks the exact target state immediately before mutation. Transaction-capable DML runs in an explicit transaction and commits only after every postcondition passes; any error rolls back the mutation while retaining the backup. A DDL or other change without an equivalent safe transaction and recovery boundary stops and returns to planning or a human decision. Successful completion emits exactly one terminal outcome: `APPLIED` after committed mutation, or `NO_OP` after an integrity-valid existing backup and complete postconditions prove no write is needed. An SQL error, missing outcome, or any other value is unsuccessful. The primary SQL never deletes or overwrites the backup. Safe recovery is a readiness requirement for data-changing SQL: UPDATE or DELETE must restore exact backed-up rows, INSERT recovery must remove only stable keys created by that operation, and DDL or transformation without truthful recovery stops and returns to planning or a human decision. Recovery never runs automatically or masquerades as safe through broad predicates, inferred keys, or fabricated rollback. The same logical backup name may be reused for a separately authorized new operation only after human cleanup and fresh pre-mutation proof. The backup otherwise remains after the primary operation until that cleanup is performed. No cleanup SQL is generated, retained in the primary artifact, or invoked by `pre-execute-issue`, `execute-issue`, closeout, target verification, or push delivery.
