# Deliver Issue lanes through native subagent lanes, not a required pi-workflow host

`/run-issue-workflow` keeps sole delivery authority. The **Domain action reducer** still decides every legal action, the per-Run journal still owns Grants, budgets, retries, repair waves and outcomes, and the `execute-issue` and `close-issue` leaves still own their Issue worktree, verification, review, integration and closure. What this ADR changes is only the **execution material** beneath that authority: one Issue lane is a native subagent lane — a `worker` child launched through `pi-subagents` with its own managed worktree — and no longer a `pi-workflow` dynamic-stage generated agent task whose publication runs through `establishRawOwner`.

This supersedes the clauses of [ADR-0076](0076-schedule-delivery-through-pi-workflow-with-a-domain-action-reducer.md) and [ADR-0077](0077-split-durable-delivery-state-by-owner-and-hard-cutover-the-substrate.md) that make the `pi-workflow` bundle the required materialization of delivery actions. ADR-0076's domain-action-reducer ownership and ADR-0077's owner-split of durable state remain in force, as do ADR-0040's sole Start authority, Issue-lane isolation, leaf execution and closeout ordering, and [ADR-0059](0059-one-owner-per-seam.md)'s one-owner-per-seam. `pi-workflow` becomes one optional materialization of the same facts: it may be re-adopted without changing the journal, the reducer, or the Grant.

Reason, measured rather than argued. The repository's own fit record already marked this capability `blocked`: `docs/agents/pi-workflow-fit-evidence.md` AC-2 records `Mutation-capable task artifact publication` as blocked, with the run staying `running` until explicitly stopped, reproduced in three probe runs. Run #108 then reproduced it in real delivery: Issue #109 was implemented and verified (candidate `c3bb89f`, clean Standards and Spec, focused and full suites passing), yet the lane task never settled, `result.json` and `raw.md` were never written, the controller stayed `suspended_waiting_children`, and no close request was ever recorded. `dist/workflow-raw-contract.js` requires `realpath(task.cwd) === project` while `dist/worktree.js` sets `task.cwd` to the managed worktree, and `dist/dynamic-generated-task-runtime.js` forces that worktree for any non-read-only capability — so every delivery lane is on the failing path and no Spec content can avoid it. Filed upstream as AgwaB/pi-workflow#16, with the correction that `@agwab/pi-subagents`'s containment rule is deliberate and the inconsistent side is the reader.

Two operator rules bound every Run. Dependency order comes only from the published blocker edges, and a dependent Issue becomes ready only when each blocker is closed in the tracker, its candidate is reachable from the target, and its worktree is absent. A Run records a hard leaf budget in its **DAG Run Grant** — at most ten `execute-issue` and ten `close-issue` invocations — counted from the journal so a restart, a replacement lane, or a re-entry cannot reset it; reaching it stops the Run fail-closed with the exact counter evidence.

Consequences. Readiness must treat the lane-settlement capability as a required public surface, alongside the prerequisites [ADR-0079](0079-amend-the-setup-bootstrap-for-the-pi-workflow-substrate.md) already names, so `READY` is never claimed from a probe set that cannot detect the failure this ADR avoids. The bundle, its controller, and the host-record lane-evidence reader are retired from the delivery path; `pi-workflow-host.mjs`'s action planning, the reducer, the journal, `issue-lane.mjs`, and the operation identity all remain. CONTEXT.md's **delivery host** entry currently defines that term as the `pi-workflow` run, and must be re-synced with this decision.

Basis: human decision in the Pi session of 2026-09-17 — "重新設計能夠實作 multi issue": use a DAG to complete Issues in order, cap `execute-issue` and `close-issue` at ten invocations each, and confirm a design that completes reliably and stably. The rejected alternatives were waiting for the upstream fix as the only path (leaves the workflow unusable for every mutation-capable lane), editing a child's Acceptance Criteria to add the missing prerequisite (its body digest is bound into the published decomposition, so the change invalidates this Run's Grant binding and forces a new Run), and replanning the same Spec on the same substrate (the failure is content-agnostic).
