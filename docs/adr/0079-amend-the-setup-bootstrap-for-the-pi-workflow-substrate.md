# Amend the setup bootstrap for the pi-workflow substrate

`/setup-matt-pocock-skills` remains the single approved operational bootstrap of [ADR-0072](0072-make-setup-an-approved-operational-bootstrap.md). This ADR amends that decision's substrate assumptions; it does not supersede its direction. ADR-0072 still requires setup to present one bounded owner plan, to mutate only after one explicit human acceptance, and to return `READY` only when the selected workflow can actually proceed.

**Readiness keeps the installation boundary.** `READY` continues to require that the selected `run-issue-workflow` package is installed and that every managed entry the current environment resolves points at that exact package version. Excluding the installation boundary was rejected: an absent, foreign, or misdirected entry would then still yield `READY`, which is the false-readiness failure ADR-0072 exists to prevent.

A **managed entry** is a harness-discoverable public link — not a copy — whose resolved target is exactly `<cache>/versions/<packageVersionId>/<skillPath>`, and whose `realpathSync.native` agrees with that target. Installation evidence requires the complete set for the environment and rejects both a subset and a superset of it, and rejects any entry that resolves elsewhere. Installation, backup, exclusive replacement, and read-back of those links stay owned by `skills/personal/run-issue-workflow/scripts/workflow-installation.mjs`; setup orchestrates and reads back that owner's receipt rather than reproducing it.

**Entry destinations are environment-derived, not hardcoded.** The current owner derives its set from the cache location as `<codexHome>/skills/run-issue-workflow` plus `<codexHome>/../.agents/skills/run-issue-workflow`. Readiness must instead cover every destination the current environment actually resolves. A destination that resolves into a source checkout rather than the selected package version — the defect class `94757a4` fixed for the development linker, whose earlier link at `~/.claude/skills/run-issue-workflow` still points into the working tree — is not `READY`. Readiness binds the selected package version to the environment's resolved entries; it does not by itself require the newest target commit to be the installed version.

**What ADR-0078 retired.** [ADR-0078](0078-retire-the-installed-package-qualification.md) retired Issue 91's WSL-bound qualification evidence: the component fixture, the three retained samples, and any delivery-time measurement inferred from them. It did not retire the installer, the installed entry, the managed-entry read-back, or their tests, all of which remain in force and reachable. Where ADR-0078's prose suggests the package and installed-entry surfaces themselves do not survive the move to `pi-workflow`, this ADR resolves the reading in favour of the surviving implementation: the retired part is the qualification evidence and its measurement claim. Readiness must therefore not depend on a retained qualification sample, including one that happens to exist in the host's qualification store.

**Substrate clauses that no longer hold.** The retired host driver, loopback control bridge, and Windows managed-entry pair are not readiness requirements, and the delivery host is launched by path from the selected package per [ADR-0076](0076-schedule-delivery-through-pi-workflow-with-a-domain-action-reducer.md) and [ADR-0077](0077-split-durable-delivery-state-by-owner-and-hard-cutover-the-substrate.md). The GitLab `to-tickets@v2` prerequisite that the retired decomposition treated as separate is satisfied in source. The consumers that decomposition named — Issues #88, #90, and #91 — are closed, with #91 closed as superseded under ADR-0078.

**Retirement.** Issues #92 through #95 are retired as superseded: their frozen planning baseline, seal, decomposition, and #95's child contract no longer describe the target. The replacement Spec is published by primary `/to-spec` from this ADR's scope and re-derives its own children. Constraints 1 through 6 and 8 of the retired #92 text carry forward unchanged, constraint 7 carries forward as amended above, and constraints 9 and 10 are discharged by those closures and by the committed adapter.

This ADR records the amended architecture and grants no installation, tracker, commit, publication, push, or deployment authority beyond the single scoped seal commit that carries it.

Basis: human decision B in the Pi session of 2026-09-17, retaining the installation boundary after the coordinator's earlier preference for excluding it was rebutted by `skills/personal/run-issue-workflow/scripts/workflow-installation.mjs` and by the live managed entries on this host. Deferring the choice to the replacement Spec's planning lane was rejected because the readiness boundary is what the Spec's acceptance criteria must encode.

Reversal or validation: before the replacement Spec reaches Run-ready, confirm that each amended clause names an owner that exists at the selected target, and that no carried constraint depends on the retired qualification samples. Reverting to installation-free readiness requires evidence that setup cannot report `READY` while a managed entry is absent or misdirected.
